# Convenções comuns dos comandos SDD

> Fonte única (ex-§3.0 do method-guide) das convenções que todo comando `/keelson:*` segue
> sem redeclará-las. Guia humano do método: `docs/_meta/method-guide.md`.

- **Cabeçalho ≠ front-matter.** SPEC, PLAN e TASK **não** têm YAML front-matter: os metadados (`**Status**`, `**Brief**`, `**Jira**`, `**Funcionalidade**`…) são linhas markdown `**Chave**: valor` logo abaixo do `# TÍTULO`. YAML delimitado por `---` só existe em HANDOFF, perfis de `guidelines/` e frontmatter de commands/agents/skills. Onde a doutrina disser "front-matter" de um artefato SDD, leia-se **cabeçalho markdown** — localize com `grep -n '^\*\*Chave\*\*:'`, nunca com parser de YAML.
- **Formas canônicas para contar/localizar IDs** (a lista da SPEC é bullet, o heading não; contagem com o padrão errado devolve zero em silêncio): FR/NFR/AC → `grep -c '^- \*\*FR-'` (idem `NFR-`/`AC-`) · FEAT → `grep -c '^### FEAT-'` · TASKs de um slug → `ls tasks/TASK-*.md | grep -v INDEX` (o glob cru inclui os `TASK-NNN-INDEX.md`, que são panorama, não tarefa). Contagem que der `0` num artefato notoriamente populado é sinal de padrão errado, não de artefato vazio — confira o formato real antes de concluir.
- **Selos de evidência (decisão 4.96).** Premissa da §8 da SPEC carrega dois eixos ortogonais: a **origem** (`[assumido]`/`[confirmar]` — quem decidiu) e o **selo de evidência** (`[evidência: <nível>]` — o que a sustenta). Escala fechada: `crença` (opinião/intuição, nada observado) · `anedota` (1–2 relatos, não sistemático) · `entrevistas` (padrão ouvido de 3+ fontes) · `medido` (número de produção/experimento). O selo **nunca bloqueia**: `crença`/`anedota` sustentando requisito central é matéria da crítica de mérito (`product-analyst`) e da resolução do PO — a SPEC segue com a aposta **declarada**. Forma canônica textual (grep-friendly); emoji é decoração opcional, nunca o dado.
- **Ficha primeiro.** Ler `keelson.config.json` na raiz antes de qualquer coisa — dela vêm `docsRoot`, `codePaths`, `profile`, os comandos de qualidade (`quality.*`) e os `gates`. Nunca assumir caminhos ou comandos fixos. O leitor canônico é `${CLAUDE_PLUGIN_ROOT}/scripts/ficha.sh` (decisão 4.151): `--get <chave.pontuada>` (valor cru; array um por linha), `--screen-verify` (normaliza o atalho booleano legado) e `--resolve-profile <role>` (aplica o prefixo `plugin:` — errar essa resolução carrega o perfil errado em silêncio). Exit 3 = degradado com causa nomeada em stderr → leia a ficha com os próprios olhos e **declare** a degradação (mesma régua do graph-contract §5).
- **Perfil de linguagem ativo.** Resolvido pelo campo `profile.<role>.file` da ficha: prefixo `plugin:` → `${CLAUDE_PLUGIN_ROOT}/guidelines/<resto>`; caminho simples → relativo à raiz do projeto; campo ausente → exemplar do plugin com a mesma `lang`, senão `guidelines/project/<role>/`. Perfil com `reviewed: false` no front-matter → avisar que está pendente de revisão humana. A doutrina `${CLAUDE_PLUGIN_ROOT}/guidelines/core/*` **vale sempre** (aderência é gate — implement, princípio 2); a **carga** segue o mapa: main session dos comandos não lê core/* (specify é agnóstica por regra própria; plan/tasks/implement carregam Charter+perfil conforme seus corpos); /keelson:auto lê só a tabela de rigor/papéis de WORKFLOW.md na triagem; cada subagent lê os core/* que seu corpo lista. PERFORMANCE.md: developer/code-reviewer o carregam quando a task toca consulta, laço sobre volume variável ou renderização pesada (mesmo gatilho da seção de performance do perfil); o `performance-engineer` o lê sempre — é o gabarito do gate 10 (4.155). DESIGN.md: developer o carrega quando a task toca superfície de interface (mesma lista canônica da description do `product-designer` — prevenção antes do gate); o `product-designer` o lê sempre — é o gabarito do gate 11 (4.218). Some as lições do projeto (`guidelines/project/`). **Releitura é exceção declarada** (4.35/4.103): perfil, convenção ou doutrina já lidos nesta sessão não se releem na íntegra — relê-se a **seção** que faltou (`sed -n`/offset); e a carga do perfil é sempre **por seção** conforme o gatilho do corpo de cada comando/agent, nunca o arquivo inteiro por hábito.
- **Memo de exploração.** Exploração de código/domínio é salva em `thoughts/local/exploration-<slug>.md` (concisa: caminhos + mecanismo); as etapas seguintes leem o memo em vez de re-explorar e o complementam se faltar detalhe. O memo é snapshot — antes de editar, vale o arquivo real.
- **Estado de run (guarda anti-parada).** Execução de waves mantém `thoughts/local/run-state-<slug>.md` — formato canônico (uma linha por campo, exatamente estas chaves):

  ```md
  status: em_andamento
  slug: <slug>
  plan: PLAN-MMM
  waves_concluidas: <X>
  waves_total: <N>
  retomada: {docsRoot}/<slug>/INDEX.md + {docsRoot}/<slug>/tasks/TASK-MMM-INDEX.md
  sessao: <id da sessão que escreveu, ou "desconhecida" sem fonte de id>
  ```

  O escritor canônico é `${CLAUDE_PLUGIN_ROOT}/scripts/run-state.sh <raiz> init|wave-done|close|remove <slug> …` (decisão 4.151 — as chaves nunca nascem erradas de memória): o `/keelson:implement` roda `init` antes da primeira wave e `wave-done` a cada final de wave; a Entrega (Etapa 5 do `/keelson:auto`, ou o output final do implement avulso) roda `close <motivo>`/`remove`. O hook `wave-guard` (Stop) lê este arquivo **fora do contexto do modelo** — imune à sumarização — e bloqueia encerramento de turno enquanto `status: em_andamento` (decisões 4.23/4.24). Parada legítima (Entrega feita, degrau 3 com pergunta já disparada, pedido explícito do humano) muda `status:` para `encerrado — <motivo>` antes de encerrar. **Posse e terceira saída (sessões paralelas no mesmo checkout — decisão 4.251):** o run é de quem o escreveu — `sessao:` nasce de `RUN_STATE_SESSAO`, senão `CLAUDE_CODE_SESSION_ID` (o mesmo UUID que os hooks recebem como `session_id` no payload), senão `desconhecida`. Run cuja `sessao:` aponte **outra** sessão não é "fôlego" nem parada vetada — é posse de terceiro, e as duas saídas habituais são destrutivas (continuar = entrar na worktree de uma sessão viva; encerrar = apagar o checkpoint dela no meio de uma TASK): não edite o arquivo, não continue a wave — **inventarie** (mtime do run-state, `git status` da worktree apontada em `retomada:`, sessões pares vivas) e **escale ao humano** nomeando o achado. O escritor reforça mecanicamente: `init`/`wave-done`/`close`/`remove` recusam (`exit 2`) run `em_andamento` de terceiro quando ambos os ids são conhecidos (algum lado `desconhecida` → degrada ao aviso, nunca bloqueio cego; `FORCE=1` assume a posse de propósito). Na outra ponta, o hook `compact-anchor` (SessionStart pós-compactação — decisão 4.146) reinjeta estes campos como contexto assim que a janela é comprimida: estado de run se re-deriva **do disco** (releia os artefatos de `retomada:` antes do próximo despacho), nunca do resumo comprimido.
- **Report de subagent — duas camadas (decisão 4.103).** O retorno de um agent do ciclo à main session é **somente o YAML do contrato dele** — sem prosa antes ou depois, campos textuais (`notas`, `detalhe`, `sumario`) em 1–3 linhas cada. A narrativa longa (explicação de implementação, contexto amplo de achado, evidência extensa) vive no **artefato durável** que a doutrina já designa — closure da TASK, ledger, INDEX, o próprio commit — nunca no retorno: **retorno é sinal para a orquestração; artefato é memória** (mesma régua da 4.76 — o report final lê disco, não relê sessão; o retorno integral na janela da main é pago de novo a cada turno até o fim do ciclo). Calibração: achado de gate carrega o necessário para o retry (âncora `arquivo:linha` + motivo + ação) — **completo no acionável, econômico em todo o resto**; aprovação sem achados é o YAML mínimo do contrato. O contrato vale em **qualquer canal de retorno** — despacho aguardado, notificação de background ou, no modo teams, a mensagem do teammate ao lead via `SendMessage`: muda o transporte, nunca o formato (decisão 4.292; fatos do modo em `agent-teams.md`).
- **Ledger de sessão (matéria-prima do report — decisão 4.76).** O relatório final não se reconstrói de memória: cada evento que ele vai narrar é **escrito no instante em que acontece**, num arquivo próprio sob `thoughts/local/session-ledger/`. Motivo: num ciclo longo o contexto é comprimido e o detalhe (quem revisou, por que decidiu assim, o que o conector devolveu) some — é a mesma régua do rastro durável do sync (§0 do protocolo Jira). O relatório final **lê a pasta**, não relê a sessão.

  - **Um arquivo por evento** — nunca append num arquivo compartilhado: waves rodam em paralelo (worktrees no modo teams) e o `thoughts/local/` de um worktree **não é** o do working tree principal. Nome ordenável, corpo curto:

    ```md
    thoughts/local/session-ledger/<yyyymmdd-hhmmss>-<tipo>-<origem>.md

    ts: 2026-07-31T14:23:10-03:00 · tipo: gate · origem: code-reviewer · slug: <slug>   ← linha do ledger.sh, nunca do corpo
    TASK-003 aprovada no retry (gate 4: duplicação em <arquivo>) · revisado_por ≠ implementado_por
    ref: {docsRoot}/<slug>/tasks/TASK-003-*.md
    ```

    O caminho resolve **sempre na raiz do repo principal** (`git rev-parse --show-toplevel` do working tree principal), nunca dentro do worktree do agent. Timestamp medido pelo próprio `ledger.sh` (decisão 4.156): o corpo passado pelo stdin são **só as 2–3 linhas de conteúdo** — a linha `ts:` do cabeçalho e a `ref:` (via `--ref`) são do script, e linha `ts:` escrita de memória no stdin é **descartada** no append (ts estimado não entra em evento).
  - **Quem escreve é o Tech Lead** (main session). Os avaliadores (`code-reviewer`, `qa`, `security-engineer`, `performance-engineer`, `product-designer`) são read-only por desenho e **não ganham `Write` para isso**: quem recebe o report do agent anota o evento em 2–3 linhas. No modo teams, o Tech Lead anota ao consolidar a wave. Mesma régua para o **retorno** do parecer em teams (decisão 4.292): o harness injeta `SendMessage` no teammate mesmo com `tools:` só de leitura — faltar ferramenta nunca é diagnóstico para conceder `Write`/`Edit`/`Bash` a avaliador "para conseguir devolver" (anti-padrão de campo: o canal existe; o que faltava era conhecê-lo).
  - **Catálogo fechado** — só estes tipos entram; o que não está aqui não vira evento (senão o ledger vira log de tudo e custa mais do que economiza): `gate` (resultado + `implementado_por`/`revisado_por`) · `decisao` (decisão em nome do Diretor) · `intervencao` (resposta **efetiva** do Diretor no meio do ciclo — veto na janela, resposta a escalação ou pergunta, handoff devolvido; anotada no instante em que a resposta chega, com a natureza em meia linha no corpo — decisão 4.244. `decisao` é o inverso — autonomia exercida em nome dele — e **nunca** conta como intervenção) · `fora_de_escopo` · `pendencia` (estacionada, handoff, achado não corrigido) · `tracker` (sync degradado, com a evidência literal do que a chamada devolveu) · `marco` (largada/etapa/entrega, para a linha de duração) · `wave_sequencial` (condição que forçou uma wave de 2+ tasks a sequencial, com a família — recurso compartilhado ou dependência/risco; é a série da medição condicionada pela 4.157 — decisão 4.301).
  - **Não duplica dono.** Fato que **sobrevive à sessão** continua indo para onde já ia — `INDEX.md` (furo no plano, sync pulado, riscos ativos, closure), `Cronologia` do BRIEF (tempo, na rota formal), `learning-log.md` (lição de processo, do `agile-coach`). O ledger guarda o que hoje **só existe no contexto** e morre com ele. Régua: *sobrevive à sessão → INDEX; serve ao report desta sessão → ledger*.
  - **Nunca é gate.** Ledger ausente, vazio ou incompleto não bloqueia nada e não consome retry: o report sai com a **lacuna nomeada** em meia linha (mesma degradação da linha de duração). Ele é insumo de transparência, não permissão.
  - **Ciclo de vida.** Consumido pelo report → mover os arquivos para `thoughts/local/session-ledger/reported-<yyyymmdd-hhmmss>/` (mesmo precedente do memo de exploração removido na closure e do run-state removido após o push). Sem esse corte, o próximo relatório repete evento velho. Nada disso é versionado (`thoughts/` está no `.gitignore` pelo `/keelson:init`). A mecânica — nome ordenável, timestamp medido, catálogo fechado validado, arquivamento preservando pendentes — é do `${CLAUDE_PLUGIN_ROOT}/scripts/ledger.sh <raiz> append|list|count|archive` (decisão 4.151; corpo do evento pelo stdin, pendente preservado com `--keep`); **o que** anotar e **quando** continua sendo desta doutrina.
- **Ferramentaria descartável na árvore do consumidor nasce sob `thoughts/local/` (decisão 4.184).** Instrumento de prova que precisa rodar no runtime do projeto (ex.: tokenizer do próprio interpretador via container que só monta o repo) não alcança o scratchpad da sessão — scripts, snapshots de base e listas de lote nascem sob `thoughts/local/tools/<propósito>/`, nunca num diretório novo da raiz nem numa pasta do projeto que "parece temporária" (caso real: diretório untracked e não-ignorado na árvore, sujando o `git status` e a um `git add -A` de distância do commit). A cobertura já é garantida pelo `/keelson:init` (Etapa 5.5), mas **se prova, não se infere** (4.51): `git check-ignore` na criação. Remoção — ou arquivamento — **declarada no fecho**, como o memo de exploração e o run-state.
- **Artefato citado fora do slug viaja com o caminho (decisão 4.124).** A numeração de SPEC/PLAN/TASK é **por slug** — o mesmo `PLAN-002` existe em quantos slugs o repo tiver, então o ID nu só identifica algo **dentro** do próprio slug. Teste: **o texto sai do slug?** (próximo comando, comando de retomada, report, boletim, escalação — tudo que o Diretor pode copiar para uma sessão limpa) → cite o **caminho relativo do arquivo real** (`{docsRoot}/<slug>/plans/PLAN-MMM-<nome>.md`), nunca o ID nu — os comandos `/keelson:*` aceitam caminho por contrato, e `--slug=` no texto ao lado não basta: num copy-paste as duas partes raramente viajam juntas. Dentro de artefatos do próprio slug, o ID curto continua canônico. No sentido inverso (entrada), ID nu que casar arquivo em **mais de um slug** → **parar e listar os candidatos com caminho** — nunca escolher por conta.
- **Resolução de slug.** Dona é a Etapa 0.2 do `/keelson:specify`: reusar slug de domínio existente (inclusive legado — que primeiro migra) antes de criar novo; na dúvida, perguntar ao humano.
- **Modelo de cada spawn vem da ficha; o frontmatter é o default.** Ao despachar um agent do keelson, rode `bash "${CLAUDE_PLUGIN_ROOT}/scripts/ficha.sh" <raiz> --get models.<agent>` (chave = o `name:` do frontmatter, sem o prefixo `keelson:`) e passe a saída em `model:` do spawn; **saída vazia → despache sem `model:`**, e o harness aplica o frontmatter (decisão 4.70: gerador barato, avaliador caro — rebaixar avaliador é decisão do projeto, declarada na ficha, nunca chute de quem despacha). Valor = alias de modelo do harness (ex.: `opus`, `sonnet`, `haiku` — o conjunto é do harness, não deste bloco). Ficha ausente ou ilegível (exit 3) segue a mesma rota da saída vazia — o frontmatter vale, **sem** disparar a declaração de degradação do "Ficha primeiro" (exceção declarada desta leitura; na adoção inicial, antes da ficha existir, é o caso normal). Rodada que despacha vários agents no mesmo turno pode ler o bloco inteiro uma vez (`--get models` devolve o objeto) e reusar. O desvio fica na ficha — nunca no pacote instalado, que o `/keelson:update` sobrescreve.
- **Espera de subagent nunca é polling (decisão 4.118).** Resultado de agent despachado chega por **retorno** (despacho aguardado) ou por **notificação do harness** (background) — a main session nunca entra em `sleep`-loop sondando filesystem, grafo ou commit para saber se o agent terminou: cada volta de poll queima um turno e contexto à toa, e o harness já notifica a conclusão. Precisa do resultado para o próximo passo → despache e **aguarde**; pode seguir com outra frente → siga e reaja à notificação. O §4.1 do `graph-contract.md` (4.114) é a instância desta régua no fluxo de correção do grafo.
- **Despacho é por tipo, sem nome de instância (decisão 4.293).** O spawn de papel usa `subagent_type` (`keelson:<agent>` — o `agent-guard` continua negando spawn genérico com trabalho de papel, 4.42) e **não atribui nome/identidade à instância**: com Agent Teams habilitado no ambiente (`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`), subagent **nomeado** é lançado como **teammate** em qualquer sessão interativa — o retorno implícito some e a topologia do ciclo muda sem ninguém pedir (sessão não-interativa, `-p`/SDK, nunca converte). Modo teams é sempre opt-in pela flag `--force-mode=teams` (fatos e especificidades: `agent-teams.md`); o despacho anônimo é o que garante que a env var sozinha nunca converte o ciclo. **Provado mecanicamente pelo `agent-guard` (decisão 4.297)**: spawn de papel (`keelson:*`) com `name` de instância é negado uma vez, com válvula — o modo teams deliberado repete a chamada e passa; a regra textual sozinha não sobreviveu a retomada com contexto compactado (caso real de campo, reincidência da linha que fundou a 4.293). A regra governa os despachos dos comandos; sessão livre fora deles segue o default do harness. No ciclo formal (`/keelson:auto`/`/keelson:guided`), artefato SDD é commitado **no marco que o fecha** — nunca acumulado para a Entrega: a branch de trabalho nasce **na largada**, **nova por demanda** (`feat/<slug>-<descrição-curta>`; nunca reusar a branch de outra demanda por inércia — é o que mistura sobras entre entregas). **Nome — dono único desta linha (decisão 4.192)**: o default é `feat/<slug>-<descrição-curta>`; ficha com `git.branchNaming: "tracker-key"` sobrescreve para `feat/<KEY>-<descrição-curta>` com a key da raiz criada naquela largada (§16 do protocolo Jira) — sem key na largada, **fallback declarado** para o default (linha no report, nunca silêncio), e branch já pushada nunca é renomeada. **Exceção declarada (decisão 4.126)**: fatias de um épico com `**Estratégia**: unica` no BRIEF pai compartilham a **branch do épico** (`**Branch**:` registrada lá; o default que o `/keelson:specify-epic` propõe vem de `git.branchStrategy` da ficha — 4.190; a leitura é sempre do BRIEF) por contrato — a branch nasce na largada da 1ª fatia, cada fatia seguinte entra nela, e **fronteira de fatia sincroniza com a main** (merge, nunca rebase): no fecho da fatia a suíte roda pós-merge e vermelho é gate reprovado; na largada da seguinte, re-check. Reuso **não declarado** no BRIEF pai continua proibido. E o ciclo commita `docs(<slug>): …` ao fechar SPEC (com BRIEF), PLAN e TASKs; a closure de TASK commita **sempre** (`chore(<slug>): close TASK-MMM-XXX`), em qualquer modo de orquestração. Comando avulso (fora do ciclo) **não commita** — o rastro é do humano (mesma régua do `/keelson:review`). A Entrega continua dona da aceitação e do push; ela deixa de ser o único ponto de salvamento — a perda máxima passa a ser um marco, o SHA citado em closure contém a própria closure, e o diff da branch enxerga a papelada. Com `jira.enabled`, keys conforme a §15 do protocolo.
- **Commit por pathspec — o índice nunca é confiável sob concorrência (decisão 4.163).** Todo ator que commita na working tree compartilhada — developer, Tech Lead nos commits de marco/closure — usa `git commit -m "<msg>" -- <arquivos>`, nunca `git add` seguido de `git commit` sem `--`: a flag `--` ignora o que estiver no índice fora da lista, garantia do próprio git; `add`-depois-`commit` depende do estado do índice no instante do `add`, e com múltiplos agents na mesma árvore (modo SUBAGENTS, sem worktree por developer) o índice pode carregar trabalho staged de outro agente — caso real: commit de marco sem pathspec varreu um mutante de segurança que um developer havia neutralizado de propósito para provar o teste, e o bypass esteve brevemente na branch. `git add` explícito continua válido para *preparar* untracked novos, mas o commit em si sempre fecha com `-- <arquivos>`. **Exceção declarada (4.263)**: o commit de merge do `/keelson:merge` não usa pathspec — o próprio git recusa commit parcial durante merge ("cannot do a partial commit during a merge"); o controle compensatório é do comando: árvore limpa exigida na Etapa 0 e `git add` restrito aos arquivos do gatilho. **Limite da pathspec — isolamento dentro do mesmo arquivo (decisão 4.283)**: `git commit -- <arquivo>` commita o estado da **working tree** daqueles caminhos, ignorando o índice — é o que dá a garantia entre arquivos, e é o que **desfaz** a seleção de um stage parcial (`git add -p`): com hunks de duas TASKs no mesmo arquivo, o arquivo inteiro entra, hunks alheios inclusive (caso real de campo). A rota primária é **não compartilhar o arquivo na mesma wave** — sequenciar é decisão de decomposição (princípio 2 do `/keelson:tasks`, 4.106/4.228). Restando o caso, a exceção é estreita e com controle compensatório duplo, **ambos registrados no report**: `git diff --cached --stat` prova que **nenhum outro arquivo** está no índice, e `git diff --cached -- <arquivo>` confere que o staged são **exatamente os hunks próprios** — só então `git commit` **sem** pathspec (o índice conferido é a fonte). Pular a dupla conferência reabre o caso que fundou esta regra.
- **Merge limpo não é merge correto — reconciliação semântica (decisão 4.235).** Sempre que duas linhas de trabalho se reencontram — fronteira de fatia sincronizando com a main (4.126), fatias irmãs de `por-fatia` que se encadeiam, worktrees integradas (o dry-run da 4.74 prova conflito **textual**, não de valor) — o merge de 3 vias resolve por linha, nunca por significado. Antes de confiar no resultado: (1) **listar as constantes/sentinelas/contratos cujo valor difere entre os pais**, recortando pelo diff dos símbolos tocados (`git diff <base-comum>...<outro-pai>`), nunca pelo repo inteiro; (2) **varrer os consumidores novos do outro lado** desses símbolos — o perigo não está no que conflita, está no que se combina sem conflitar (caso real: 4 defeitos que só existiam no merge de fatias verdes — sentinela que mudou de valor entre os pais, bind removido de um lado e exigido do outro, asserção com premissa revogada por decisão posterior, teste apontando id antigo). O resultado do merge é **diff novo**: passa pela suíte e pelos gates da fronteira antes de seguir. Sem reencontro (branch única em dia), n/a. Merge para a base segue humano (abaixo).
- **Lista reapresentada é lista medida (decisão 4.237).** Resumo de estado ou de pendências reapresentado ao Diretor (status, report, boletim, handoff) confere cada item de pendência contra a fonte durável (INDEX, handoff, `index-check.sh`, `epic-state.sh`) antes de reapresentá-lo — lista não medida envelhece **para cima**: cobra o que já foi feito e custa a confiança da lista inteira (caso real: 3 itens já resolvidos cobrados na mesma revisão). Item cuja fonte não foi conferida sai marcado **`não medido`**, nunca reapresentado como corrente — marcação, não bloqueio (mesma degradação da lacuna nomeada do report-contract).
- **Merge, PR e deploy são humanos.** Nenhum comando faz merge, abre PR nem deploya — a autonomia termina no push da branch de trabalho (4.37/4.41). Promoção de Status (`Draft → Approved → Done`): nunca é de validator; no ciclo com BRIEF (modo autônomo), a main session promove pelo veredito `APROVAR` do `po` (4.38); sem brief ou no `/keelson:guided`, é humana.
  **Exceção declarada (decisão 4.263)**: `/keelson:merge` (humano-only) mescla uma ou mais branches, **uma de cada vez**, para dentro da branch de trabalho corrente — cada branch aprovada vira **um commit de merge próprio** (nunca um squash de N branches num commit só). Para cada branch: aplica o dry-run de conflito da 4.74 e a reconciliação semântica do item acima, e roda a suíte sobre o merge; **branch limpa (sem conflito, sem achado de reconciliação, suíte verde) fecha o commit direto, sem despachar ninguém**; havendo conflito, achado de reconciliação ou teste quebrado, delega a resolução ao `developer` **escopada só aos arquivos do gatilho** e o `code-reviewer` audita **só o diff dessa resolução** (gates 1–7, + gate 8 em área sensível), nunca a branch inteira — e só então fecha o commit de merge daquela branch antes de seguir para a próxima. O que continua exclusivamente do Diretor: push da branch resultante, merge para a branch principal remota, PR e deploy.
- **Falha de gate**: 1 retry; persistiu → escalar ao humano com o diagnóstico.
